# 默认中文在首次启动时失效：原因、修复与回归

适用版本：虎娘 / Tigirl 2026.10.7.2。

## 用户可见行为

新安装或首次激活输入法时，即使“默认中文”已勾选，输入法也可能以英文接管状态开始工作。重新保存设置后，中文又能生效。本次修复使首次激活遵守所配置的默认模式，同时保留用户主动切换中英文的行为。

“默认中文”是新服务激活时的初始值。新上下文继承当前线程模式；返回已有上下文时恢复该上下文的模式。普通配置刷新保留当前模式；修改设置并保存后，会通过重载请求重新应用配置的默认模式。无实际改动的保存不产生重载请求。因此它不表示每次焦点变化都强制切回中文。

## 原因

配置解析正确：`Config::defaultChinese` 默认是 `true`，缺少配置文件或缺少“默认中文”键都保持默认值。设置界面的勾选状态也来自同一配置。问题出在 TSF 的后续模式通知。

在真实 Windows 前台激活流程中，跟踪到以下顺序：

1. `Service::ActivateEx` 按配置启动中文，并发布 OPENCLOSE=1、含 NATIVE 位的 CONVERSION 状态。
2. 窗口取得真实前台焦点后，`msctf.dll` 在仍然有效的 conversion compartment 上发送 `OnChange`。
3. 此时 `GetValue` 返回 `S_FALSE`，值类型为 `VT_EMPTY`，表示该状态尚未有值。
4. 旧 `ModeCompartments::changed` 将这个空状态当成数值 0，向引擎通知英文，再主动发布 CONVERSION=0、OPENCLOSE=0。
5. 首字母经 `ITfKeystrokeMgr::TestKeyDown` 检查时未被中文输入法接管。

Microsoft 对 [`ITfCompartment::GetValue`](https://learn.microsoft.com/en-us/windows/win32/api/msctf/nf-msctf-itfcompartment-getvalue) 的说明明确区分未设置值（`S_FALSE` / `VT_EMPTY`）与实际存储的值。空状态本身并不代表用户请求英文。

修改设置并保存会产生新的 `_native_settings_reload` 标识。服务收到这一明确重载请求后，重新应用“默认中文”，所以保存后看似恢复正常。单纯补写默认配置键无法解决后续空状态覆盖模式的问题。

## 修复

生产改动集中在 `native/tsf/ModeCompartments.cpp` 的 `changed`：

- 使用既有 `read` 的初始化状态输出，区分无值与显式数值。
- 无值通知执行 `publish(desired_)`，重发最新请求的模式，不触发引擎中英文切换回调。
- 真实的数值 0 仍按英文请求处理，含 NATIVE 位的有效状态仍按中文处理。
- 复用既有写入重入保护与延后重试机制。如果 Windows 暂不允许在通知回调内写入，延后处理仍跟随最新请求。
- 用户在旧重试执行前明确切成英文时，以新的英文请求为准；关闭服务会取消旧重试。

没有新增安装期模式写入、profile 通知 sink 或每次聚焦强制中文的规则。

## 真实启动回归

回归代码为 `tests/startup_mode_fixture.h`、`tests/startup_mode_test.py`，通过 `tests/tsf_host.cpp` 的独立探针入口运行。使用独立用户数据目录、私有 COM 清单和进程内 profile 激活，保持日常安装注册与个人配置不变。

先激活目标 profile，再显示测试窗口并取得真实 Windows 前台焦点。此流程不预先手工设置中文，也不向日常应用注入物理按键；首字母是否接管由真实 TSF `TestKeyDown` 接口判断。旧的常规输入测试会在开始前主动设中文，因而不能单独证明默认模式生效。

| 配置情况 | 旧版真实前台启动 | 修复后真实前台启动 |
| --- | --- | --- |
| 没有配置文件 | 被错误切成英文 | 中文，首字母接管 |
| 配置缺少“默认中文”键 | 被错误切成英文 | 中文，首字母接管 |
| 明确“默认中文 是” | 被错误切成英文 | 中文，首字母接管 |
| 明确“默认中文 否” | 英文 | 英文，首字母透传 |

在同一 Windows ARM64 设备上，ARM64X 完成四种配置乘以隐藏 / 真实前台的 8 个场景；x64 与 Win32 组件各完成四种配置的真实前台场景。修复后的 16 个启动场景全部通过，配置文件内容及安装注册路径均未改变。x64 / Win32 验证使用该设备的对应运行环境，不能代替每台用户电脑上的安装验收。

修前与修后 ARM64X 对照使用相同测试宿主、相同实际词典与相同配置。修复后仍可看到 Windows 发来的空 conversion 通知，但服务重新发布中文，OPENCLOSE 持续为 1。

## 定点边界回归

新增 `tests/ModeUnsetCompartmentProbe.vcxproj`、`tests/mode_unset_compartment_probe.cpp` 和 `tests/mode_unset_compartment_test.ps1`。

这组测试直接编译生产 `ModeCompartments`，使用真实 TSF 存储、事件订阅和消息分发。薄包装定点注入实际前台路径中出现的有效接口空值通知，以及一次回调内写入拒绝。它与上面的真实操作系统启动复现分别验证触发路径与边界行为。

12 个场景覆盖中文 / 英文、open / conversion 空通知、即时 / 延迟写入、明确英文先于旧重试、已有待处理英文再收到空值，以及关闭后重新以英文打开。修复后 12 / 12 通过；从修改前源码快照提取的负控为 2 通过、10 失败，符合预期。无值通知不产生上层模式切换回调，明确英文只产生一次有效回调。

单独调用公有 `ClearCompartment` 与上述 Windows 路径不同：公有清除会断开旧接口，旧接口返回 `E_UNEXPECTED`，重新取得的接口才显示无值，并没有相同的事件通知。因此公有清除测试不作为本问题的直接复现证据。

## 证据与升级

构建工作区的 `build/default-chinese-20261007/` 保存启动跟踪、修前快照、修后结果、定点负控来源和打包校验。分发目录的“源码与许可 / 虎娘-校验信息.json”记录该发布版本的验证与源码对应关系。

升级后保留个人配置与学习记录，无需取消再勾选“默认中文”，也无需清空用户数据。应重新启动使用过输入法的应用，使其加载新版本 DLL；仍驻留旧 DLL 的进程不会自动获得本次修复。
